# StreamVista Intelligence — Input Data Flow

## Principle

**Data first → validation second → AI analysis third → deterministic validation fourth → operator approval last.**

The Intelligence surface analyzes StreamVista data; it does not invent StreamVista data.

## Flow

StreamVista source data → verified/operator-approved inputs → `/intelligence` UI → structured JSON → server-side Intelligence API → validation + rights/commercial constraints → AI context assembly → configured AI provider → structured output → deterministic validation/calculation → `/intelligence` UI → operator review → approved strategy/revenue intelligence.

## Data classes

- `verified`: directly sourced from StreamVista systems.
- `operator-estimated`: entered or approved by the operator.
- `ai-derived`: generated by the Intelligence model.
- `unknown`: unavailable and must remain unavailable; never fabricate a value.

## UI request

The browser sends structured JSON. It must not send a free-form analysis prompt as the primary contract. A request contains project context, optional buyer context, version inputs, rights, commercial context, operator constraints, and analysis flags.

## Server responsibilities

The server authenticates the caller, optionally resolves the selected title and buyer from Supabase, resolves existing rights for a selected StreamVista title, validates numeric ranges and data-status values, builds the AI context, calls the configured provider, parses structured output, and performs deterministic yield arithmetic.

Provider credentials are server-only. The browser never receives provider keys.

## Deterministic arithmetic

For a version with revenue `R` and revenue share `S`, net yield is `R × S / 100`. Missing revenue or share produces `UNKNOWN` for that version's net yield. The aggregate total is the sum of known deterministic version yields; AI output cannot override this arithmetic.

## Audit metadata

Every successful execution response carries project ID, operator ID, provider, model, provider request ID when exposed by the provider, and timestamp. Persistence of an execution snapshot should be added to the production audit store once its canonical schema/table is established; this change does not silently invent a new production table.

## Current implementation

- Web route: `/intelligence`
- API route: `POST /api/intelligence`
- Authentication: existing StreamVista Supabase session/JWT middleware
- Source tables used when IDs are supplied: `sv_app_titles`, `sv_app_profiles`, `sv_title_rights`
- AI gateway reuse: existing `AIProviderGateway`
- Provider selection: `INTELLIGENCE_AI_PROVIDER` and `INTELLIGENCE_AI_MODEL` server environment variables; no provider secret is exposed to the client
- Branch: `feature/intelligence-data-flow`
